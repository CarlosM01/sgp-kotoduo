## Ejecuciones

### E1 — `v0.9` · 2026-11-26
- **Estado:** Fallido
- **Obtenido:** cabeceras: 12/12 respuestas con `Content-Security-Policy` (con `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options` (`DENY` en el cliente, `SAMEORIGIN` en la API) y `Referrer-Policy: no-referrer`; 0/12 con `X-Powered-By`; `Server: nginx` sin versión. HSTS: 0/7 en las respuestas de nginx y 5/5 en las de la API (`max-age=31536000; includeSubDomains`), sin efecto por HTTP → no aplicable en local. `npm audit --omit=dev`, `npm audit` y `--audit-level=high`: "found 0 vulnerabilities" (0 info/low/moderate/high/critical; 439 dependencias, 112 de producción). Secretos: 0 claves privadas; 1 coincidencia de token (JWT falsificado de `api/test/integracion/autorizacion.test.ts`); las asignaciones encontradas son marcadores de `.env.example`, secretos de prueba y nombres de variables; `.env` ignorado (`.gitignore:4`) y ningún commit lo agregó; el log de `sgp-api` tiene 1 línea y 0 coincidencias de JWT, contraseñas o `Authorization`. `sgp_app`: `permission denied for table movimiento_insumo`, `permission denied for table outbox_evento`, `permission denied for schema sgp` (y `public`); `SELECT` permitido. **Pero la API del stack se conecta como `sgp`** (`DATABASE_URL` del contenedor), rol con `rolsuper = t`, no como `sgp_app`: las restricciones de R7 y R8 no se aplican a la aplicación en ejecución.
- **Evidencia:** `evidencias/E-24_cp32-cabeceras-audit.log`
- **Defecto:** DEF-02

### E2 — `v1.0` · 2026-11-26 (re-ejecución tras corregir DEF-02)
- **Estado:** Aprobado
- **Obtenido:** el compose de `v1.0` fija `DB_ROL: sgp_app`. Una sesión con las opciones que abre la API tiene `current_user = sgp_app`, `is_superuser = off` y `search_path = sgp,public`; UPDATE sobre `movimiento_insumo`, DELETE sobre `outbox_evento` y CREATE TABLE en `sgp` se rechazan por falta de privilegios. Un rol inexistente rechaza la conexión (`FATAL: role "rol_inexistente" does not exist`), sin volver al rol de login. 8/8 pruebas de `DB_ROL` en verde. Los 4 flujos E2E pasan con la API como `sgp_app` (1/1). Cabeceras: nginx, `app.ts` y los Dockerfile no cambiaron entre `v0.9` y `v1.0`, así que se conserva el resultado de E1. `npm audit --omit=dev` y `npm audit`: 0 vulnerabilidades. Riesgo residual declarado: la sesión se autentica como `sgp`, así que una inyección SQL podría ejecutar `SET ROLE NONE` (`docs/seguridad.md`). Entorno: API local (npm), no el stack Docker reconstruido.
